## はじめに

2026年10月、eMudhraが発行した中間CA証明書が、鍵生成時の乱数の弱さによって侵害されていたことが公表されました。Dart SDKにも、この件のセキュリティアドバイザリが出ています。

https://github.com/dart-lang/sdk/security/advisories/GHSA-frr6-h895-5pxp

アドバイザリによると、AndroidとWindowsの `dart:io` はSDKに組み込まれた[BoringSSL](https://www.chromium.org/Home/chromium-security/boringssl/)でTLS証明書チェーンを検証しており、OSが管理する中間証明書のブロックリストを参照しません。そのため対処には、修正済みのSDK（Dart 3.13.7 / Flutter 3.47.8）でアプリを再ビルドし、配布し直す必要があります。一方で、iOSとmacOSは、Appleの[Security.framework](https://developer.apple.com/documentation/security)で検証しているため影響を受けません。Android端末には、Google Play Services経由で同等の更新が配信されていますが、`dart:io` で通信するアプリはその更新を使えません。

![証明書の失効がアプリに届くまで](/images/b222c501f9561c/revocation-delivery.png)

設計がそうなっているから、といえばそうなのですが、直感に反します。AndroidでもiOSのように、OSで管理される証明書を利用できないのでしょうか。

---

その他、Dartには端末のproxy設定が反映されない問題があります。一部で知られている問題です。ただ気づくタイミングが切羽詰まっている状況になることが多く、知っている方は若干辛い記憶になっているのではないでしょうか。QAメンバーからの問い合わせで発覚したり、ユーザーからの特定環境で利用できない報告で発覚したりします。

https://github.com/flutter/flutter/issues/26359

俯瞰してみると、これも不思議な課題です。Android端末上から通信をしているのに、その端末に設定されたproxyが反映されません。AndroidのNative SDKを使って開発していた頃には、全く意識する必要がなかったのに、です。

## なにが原因なのか

`dart:io`における、以下の特徴が原因です。

* socketからTLSまで、ネットワーク処理をDart SDKの中に自前で実装している
* `dart:io` の実装からはJNIを呼べないため、AndroidのJava API（proxyの設定や `TrustManager`）に手が届かない
* proxyは、`http_proxy` などの環境変数しか見ず、OSの設定画面で指定したproxyを読まない
* Androidでは、ルート証明書を端末のディレクトリから直接読み、証明書の検証もSDK内蔵のBoringSSLで行う

つまりAndroidでは、自前の実装がOSの仕組みを素通りするので、OSのネットワーク設定が効きません。それなら、まあ、しょうがないか…。

## proxy、ルート証明書、証明書の検証

Security advisories によると、今回の問題はAndroid・Windowsで発生し、Linuxでもシステムの `ca-certificates` が更新されていない環境などで影響を受けます。一方、iOS・macOS では、`dart:io` が OS の `Security.framework` を利用して証明書を検証するため、今回の問題の影響を受けません。

ということは、環境によって処理が異なっていることを意味します。よくわかっていなかったのでOpusにコードを読ませながら確認してみました。

### proxy: 環境変数しか見ない (AndroidとiOS)

`HttpClient` には、接続先のURLを受け取って、使うproxyを文字列で返す `findProxy` という関数を設定できます。

https://api.flutter.dev/flutter/dart-io/HttpClient/findProxy.html

返すのは、`"PROXY host:port"`（proxyを使う）か `"DIRECT"`（直接つなぐ）です。

この関数のデフォルトの `findProxyFromEnvironment` が見るのは、`http_proxy`・`https_proxy`・`no_proxy` という**環境変数**だけです。ターミナルで `export http_proxy=...` と設定する、あの環境変数です。この処理は、AndroidとiOSで共通です。

https://github.com/dart-lang/sdk/blob/3.13.7/sdk/lib/_http/http_impl.dart#L3292-L3316

本来、AndroidのWi-Fi設定やiOSの設定アプリで指定したproxyは、**環境変数としては渡されません**。このため、OSのAPIを経由して取得する必要があります。結果、`dart:io` においては、proxyの検知が働かないようです。

https://github.com/dart-lang/http/issues/1414

https://github.com/dart-lang/sdk/issues/41376

自前で実装しようとしても、ちょっとした壁があります。`findProxy` は同期関数です。AIに調べてもらったのですが、AndroidはPAC（Proxy Auto-Config）を同期処理で実装できそうです。しかし、iOS・macOSでPACを評価するAPIは、非同期になっています。結果、両OSをサポートする実装が難しくなっています。^[[dart-lang/sdk#44971](https://github.com/dart-lang/sdk/issues/44971)]

### ルート証明書: ディレクトリを直接読む (Android)

Android向けのTLS処理は、Linuxと同じ `security_context_linux.cc` の中にあります。証明書は、端末のディレクトリから直接読みます。^[コード中のコメントによると、証明書をバイナリに組み込まないのは、バイナリのサイズを約240KB減らすためです。]

https://github.com/dart-lang/sdk/blob/3.13.7/runtime/bin/security_context_linux.cc#L43-L61

OSの設定を通らないので、こんな問題が出ています。

- [dart-lang/sdk#48056](https://github.com/dart-lang/sdk/issues/48056): 設定で無効にしたCA証明書を信頼し続ける
- [dart-lang/sdk#50435](https://github.com/dart-lang/sdk/issues/50435): ユーザーが入れたCA証明書を信頼しない

Android 14からはルート証明書が、Google Play system updatesで更新されるConscryptのAPEXモジュールに移りました。Dart 3.13.7から `/apex/com.android.conscrypt/cacerts` を読むようになるそうなので、この問題は徐々に解消していくと思われます。^[それまでは `/system/etc/security/cacerts` を読んでいたそうです]

### 証明書の検証: OSのTrustManagerを通らない (Android)

冒頭のeMudhraに関する諸問題の、根本がここです。検証をSDKに内蔵するBoringSSLが行なっているため、Androidの `TrustManager` を利用しません。

結果、OSが配る中間証明書のブロックリストが効かない、という事態になったようです。Flutter 3.47.8（Dart 3.13.7）での修正は、次の2つです。

- [dart/568000](https://dart-review.googlesource.com/c/sdk/+/568000): Dartに内蔵するBoringSSLを更新し、侵害されたeMudhraの中間CA証明書をブロックする
- [dart/64696](https://github.com/dart-lang/sdk/pull/64696): Android 14以降で、更新可能なConscrypt APEXのルート証明書ストアを使う

中間証明書のブロックリストは、アプリに組み込まれたBoringSSLの中にあります。ルート証明書はOSの更新に追従するようになりましたが、中間証明書は追従しません。もちろん中間証明書のブロックリストが頻繁に更新されるなんてことはない、はずです。ただ、この違いは把握しておく必要があると思われます。

一方で、cronet_httpを使っていた場合は、証明書の検証をAndroidの `TrustManager` が行います（後述の補足を参照）。Android端末にはGoogle Play Services経由で同等の更新が配信されているので、Cronetで通信していたアプリは、SDKの更新やアプリの再ビルドを待たずに守られていたことになります。ただし、Google Play Servicesがない端末など、OSの更新を受け取れない端末は対象外です。

## proxyの深掘り

証明書については、改善された点がある一方で、一層の覚悟も求められることになりました。では、proxyはどうでしょうか？

---

https://github.com/dart-lang/sdk/issues/50434

proxyの問題は、P3のIssueで追跡されています。issueのコメントを確認すると、AndroidではJNIを呼ぶしかない、という点が問題のようです。

> We could also solve this issue in `HttpClient`. This would actually be fairly easy on iOS but harder on Android (AFAIK, the only way would be to make JNI calls to get the proxy configuration).

https://github.com/dart-lang/sdk/issues/50434#issuecomment-1322608466

> There is currently not a good way to make JNI calls from the `dart:io` implementation.

https://github.com/flutter/flutter/issues/20376#issuecomment-439941929

Android OSがJavaやKotlin向けに提供しているAPIなので、FFIではなくJNIが必要になり難しい、ということと筆者は理解しています。これは[ffigen](https://pub.dev/packages/ffigen)と[jnigen](https://pub.dev/packages/jnigen)の安定度の違いを見たことがある方なら、まあそうだろうなって印象になると思います。

というわけで、何かしらの回避策が必要です。

### かつての回避策: system_proxy

かつて、Flutterのアプリを手探りで実装していた頃には、[system_proxy](https://pub.dev/packages/system_proxy) などでOSのproxy設定を取ってくるのが典型的な対応でした。`main()` でなんか書いたことがあるな？ って方は、多分これです。

https://github.com/kaivean/system_proxy/blob/0ad8536e39e34befdf8119ee4796b8eaf405b92d/README.md#L37-L62

ただ、このパッケージがやるのはproxyの**取得**だけで、使い方はアプリ任せです。

proxyを通すと、今度はTLSが問題になります。CharlesやTLSインスペクションのように、proxyがHTTPSを中継する環境では、proxyの証明書を信頼しないと通信できません。でも `dart:io` は、ユーザーが入れた証明書を信頼しません。そこで、こういうコードが書かれがちです。

```dart
HttpClient()
  ..findProxy = (uri) => 'PROXY $host:$port'
  ..badCertificateCallback = (cert, host, port) => true;
```

`badCertificateCallback` が `true` を返すと、信頼できない証明書でも接続します。つまり、どんな証明書でも通るので、中間者攻撃に無防備になります。もちろん、適切に実装をすれば問題はありません。^[環境ごとに適用を切り替えたり、証明書を限定したりすればOKのはず。]

ただ、本来OSが適切に管理するべき通信が、アプリ実装者の手に委ねられてしまうのは危険です。2026年も終わろうとしている現在、そして、あれこれセキュリティに注目が集まる現在では推奨されないと感じています。

## cronet_httpとcupertino_http

OSが管理するproxyや証明書を使うのであれば、多くのAndroidやiOSのネイティブアプリと同じ通信経路を辿ればOKです。と書くとMethodChannelでリクエストを送ることをイメージするかもしれません。大丈夫です。Dartチームが用意しています。

![dart:ioとcronet_httpの経路の違い](/images/b222c501f9561c/dartio-vs-cronet.png)

| パッケージ | プラットフォーム | 中身 |
| --- | --- | --- |
| [cronet_http](https://pub.dev/packages/cronet_http) | Android | Cronet（Chromiumのネットワークスタック） |
| [cupertino_http](https://pub.dev/packages/cupertino_http) | iOS / macOS | Foundation URL Loading System（`URLSession`） |

どちらのREADMEも、`dart:io` に対する利点の1つ目にproxy対応を挙げています。

- cronet_http: "It automatically supports Android platform features such as HTTP proxies."
- cupertino_http: "It automatically supports iOS/macOS platform features such as VPNs and HTTP proxies."

Charlesに通信が出ないという [flutter/flutter#20376](https://github.com/flutter/flutter/issues/20376) も、iOSでは `cupertino_http` が使えるよ、というコメントでcloseされています。また、特にAndroidであれば、 `cronet_http` を使うことで証明書の問題も回避することができます。[OkHttp版](https://pub.dev/packages/ok_http)の開発も進んでいるので、この機会にぜひ検討してみてください。

### 補足

Opusに調べてもらった、それぞれのツールでproxyと証明書がどう扱われるかになります。本題からズレるので、気になる方はどうぞ。

:::details Cronet（cronet_http）は、Androidのproxyと証明書をどう扱っているか

**proxy**

Cronetは初期化のときに、`CreateProxyConfigService` でproxyの設定の取得元を作ります。ここで呼ぶ `CreateSystemProxyConfigService` は、Androidでは `ProxyConfigServiceAndroid` を返します。

https://github.com/chromium/chromium/blob/55adf20e5753fc93dbb0e598a501154ed5930943/components/cronet/android/cronet_library_loader.cc#L418-L445

`ProxyConfigServiceAndroid` は、JNIでJavaの `System.getProperty` を呼び、次のシステムプロパティからproxyの設定を組み立てます（[proxy_config_service_android.cc#L71-L173](https://github.com/chromium/chromium/blob/8bc08ce0f3529582e3f099dc24728de09a0037b0/net/proxy_resolution/proxy_config_service_android.cc#L71-L173)）。コード中のコメントによると、Javaの標準の `ProxySelector` とほぼ同じ読み方です。

- `http.proxyHost` / `http.proxyPort`、`https.proxyHost` / `https.proxyPort`（なければ `proxyHost` / `proxyPort`）
- `socksProxyHost` / `socksProxyPort`
- `http.nonProxyHosts` など（proxyを使わないホストの一覧）

設定の変更は、Java側の `ProxyChangeListener` で受け取ります。PACが設定されている場合、CronetはPACのURLを使わず（`set_exclude_pac_url(true)`）、Androidが用意するローカルのHTTP proxyに任せます（crbug.com/432539）。そのため、PACを評価する仕組み（proxy resolver）自体を持ちません（`CreateWithoutProxyResolver`）。

**証明書の検証**

Android向けのChromiumは、Chrome Root Storeを使う独自の検証器と、OSの検証器を選べます。ただし、Cronetのビルドでは `chrome_root_store_optional = is_android && !is_cronet_build` となり、この選択肢がありません。

https://github.com/chromium/chromium/blob/5691202e214341a5d96a3296c1b9811cce19572b/net/features.gni#L60-L66

そのため `CreateSystemVerifyProc` が使われ（[cert_verifier.cc#L30-L64](https://github.com/chromium/chromium/blob/02827ccdc9770dc1de7f2bc167e0f991ba171c46/net/cert/cert_verifier.cc#L30-L64)）、Androidでは `CertVerifyProcAndroid` になります（[cert_verify_proc.cc#L378-L379](https://github.com/chromium/chromium/blob/dcba1b2b79ba7230ad5fc3b7aa78a1775904db53/net/cert/cert_verify_proc.cc#L378-L379)）。`CertVerifyProcAndroid` はJNIでJavaの `AndroidNetworkLibrary.verifyServerCertificates` を呼び（[cert_verify_proc_android.cc#L100](https://github.com/chromium/chromium/blob/b6ae90def7daaa1d117ca983bf05dcf5e319d143/net/cert/cert_verify_proc_android.cc#L100)、[AndroidNetworkLibrary.java#L120-L127](https://github.com/chromium/chromium/blob/01b2da6c3ec1e9e61c54f2f06b3ea7cbacdb94d5/net/android/java/src/org/chromium/net/AndroidNetworkLibrary.java#L120-L127)）、最後は `X509Util` が、OSの `TrustManagerFactory` のデフォルトのトラストマネージャーで `checkServerTrusted` を呼びます。

https://github.com/chromium/chromium/blob/195962358a83d3d08c30236b80bf413002344868/net/android/java/src/org/chromium/net/X509Util.java#L517-L603

ルート証明書の選び方も、チェーンの検証も、Androidの仕組みに任されているわけです。

なお、ここで読んでいるのはChromiumのソース（Cronetを同梱する場合のもの）です。Google Play Servicesが提供するCronetも同じ作りだと考えられますが、そのソースは公開されていません。

:::

:::details URLSession（cupertino_http）は、iOSのproxyと証明書をどう扱っているか

**proxy**

`URLSessionConfiguration` の `connectionProxyDictionary` は、デフォルトが `NULL` で、その場合はシステムの設定が使われます。

> The default value is NULL, which means that tasks use the default system settings.

https://developer.apple.com/documentation/foundation/urlsessionconfiguration/connectionproxydictionary

cupertino_httpは、`connectionProxyDictionary` を設定する公開APIを持たず、内部でも設定していません。そのため、`defaultSessionConfiguration()` などから作った `CupertinoClient` は、システムのproxy設定に従います。

**証明書の検証**

cupertino_httpは、認証チャレンジを受け取るdelegate（`URLSession:task:didReceiveChallenge:completionHandler:`）を実装していません。この場合、URLSessionはデフォルトの処理を行います（`NSURLSession.h` のコメント）。サーバー証明書の検証に、アプリ側の判定は入りません。

:::

## httpパッケージとdioでの差し替え

筆者がネイティブのHTTPクライアント推しなので、簡単ではありますが、置き換え方法を紹介します。

### httpパッケージ

`package:http` の `Client()` は、Web以外では `IOClient`、つまり `dart:io` の `HttpClient` を使います。何もしなければ、同じ問題を抱えたままです。

https://github.com/dart-lang/http/blob/http-v1.5.0/pkgs/http/lib/src/io_client.dart#L14-L20

READMEの "Choosing an implementation" のとおり、プラットフォームごとに `Client` を差し替えます。

```dart
import 'package:cronet_http/cronet_http.dart';
import 'package:cupertino_http/cupertino_http.dart';
import 'package:flutter/foundation.dart';
import 'package:http/http.dart';
import 'package:http/io_client.dart';

Client createHttpClient() {
  switch (defaultTargetPlatform) {
    case .android:
      final engine = CronetEngine.build();
      return CronetClient.fromCronetEngine(engine, closeEngine: true);
    case .iOS || .macOS:
      final config = URLSessionConfiguration.defaultSessionConfiguration();
      return CupertinoClient.fromSessionConfiguration(config);
    case .fuchsia || .linux || .windows:
      return IOClient();
  }
}
```

あとは `Client` をRiverpodのProviderで配布する、などすればOKです。もしも `http.get()` や `Client()` を直接呼んでいるところがあり、置き換えが難しいならば、`runWithClient` で包みます。ただし、Flutterではコールバックが同じZoneで実行される保証がないため、包んだ範囲でも `IOClient` に戻ることがあります。

https://pub.dev/documentation/http/latest/http/runWithClient.html

### dio

dioのデフォルトも、`dart:io` を使う `IOHttpClientAdapter` です。[native_dio_adapter](https://pub.dev/packages/native_dio_adapter) を使うと、`cronet_http` と `cupertino_http` に切り替えることができます。

```dart
final dio = Dio()..httpClientAdapter = NativeAdapter();
```

Androidでは `CronetAdapter`、iOS・macOSでは `CupertinoAdapter`、それ以外では従来どおり `dart:io` を使います。^[[dio#2456](https://github.com/cfug/dio/pull/2456) を入れたので、一応timeoutも効きます。]

### 注意点

見逃しがちな点がいくつかあります。

| 観点 | 何が変わるか | 見直すこと |
| --- | --- | --- |
| 画像の読み込み | `Image.network` は `dart:io` のまま | `Client` を渡せるパッケージに置き換える |
| User-Agent | クライアントごとにデフォルトの値が違う | すべてのクライアントで明示的に指定する |
| 例外 | `SocketException` で捕まえられなくなる。dioではエラーの種類が変わる | `ClientException` で捕まえる。`DioException.type` で分けている処理を見直す |

#### 画像の読み込み

Flutter frameworkは任意のパッケージに依存しないので、`Image.network` は `dart:io` の `HttpClient` を直接使います。差し替える口はありません。^[`debugNetworkImageHttpClientProvider` という差し替え口はありますが、デバッグビルド専用です。]

画像も、`Client` を渡せるパッケージに置き換える必要があります。以下のようなパッケージが候補です。

| パッケージ | `Client` の差し替え | ディスクキャッシュ |
| --- | --- | --- |
| [http_image_provider](https://pub.dev/packages/http_image_provider) | できる | なし |
| [extended_image](https://pub.dev/packages/extended_image) | できない（内部で `dart:io` の `HttpClient` を持つ） | あり |
| [cached_network_image](https://pub.dev/packages/cached_network_image) | できる（flutter_cache_managerの `HttpFileService`） | あり |
| [taro](https://pub.dev/packages/taro) | できる（`TaroHttpClient`） | あり |

http_image_providerは、httpパッケージのREADMEが紹介している [Flutter HTTP example application](https://github.com/dart-lang/http/tree/9cdb8daf7b579745520c5b854afd3a70df5f9b2a/pkgs/flutter_http_example) で使われています。一応、公式が提案しているパッケージです。

また `cached_network_image` は、ウィジェットごとに `cacheManager:` を渡すと渡し忘れが出るので、`defaultCacheManager` ごと差し替えるのが確実です。^[flutter_cache_managerへの直接の依存が必要です。ディスクに保存するときの縮小（`maxWidthDiskCache`）も使う場合は、`ImageCacheManager` をmixinしたクラスにします。]

```dart
CachedNetworkImageProvider.defaultCacheManager = CacheManager(
  Config(
    'networkImages',
    fileService: HttpFileService(httpClient: createHttpClient()),
  ),
);
```

ちなみに、筆者は「画像だけ `dart:io` に戻る」状態をなんとかするだけなら、もっと軽量で行けるだろうと `taro` を作ってメンテナンスしています。デフォルトは `dart:io` ですが、`TaroHttpClient` を実装すれば `Client` に差し替えられます。サンプルも書いてあるので、よければご利用ください。

#### User-Agent

何も指定しないと、User-Agentはこうなります。

| クライアント | デフォルトのUser-Agent |
| --- | --- |
| `dart:io` | `Dart/3.x (dart:io)` |
| Cronet | `<パッケージ名>/<versionCode> (Linux; U; Android 15; ja_JP; <端末名>; Build/<ID>; Cronet/<バージョン>)` |
| `URLSession` | `<アプリ名>/<ビルド番号> CFNetwork/<バージョン> Darwin/<バージョン>` |

「APIはCronet、画像は `dart:io`」のように混ざると、同じアプリから2種類のUser-Agentが飛びます。揃えたいなら、クライアントごとに指定します。

```dart
// Android
CronetEngine.build(userAgent: userAgent);
// iOS / macOS
URLSessionConfiguration.defaultSessionConfiguration()
  ..httpAdditionalHeaders = {'User-Agent': userAgent};
// それ以外（dart:io）
HttpClient()..userAgent = userAgent;
```

native_dio_adapterなら、`createCronetEngine` と `createCupertinoConfiguration` に同じ設定を渡します。

#### 例外

失敗したときの例外の型も変わります。

| `IOClient` | `CronetClient` | `CupertinoClient` |
| --- | --- | --- |
| `ClientException`（`SocketException` も実装） | `CronetException` とそのサブクラス | `NSErrorClientException` |

`IOClient` の例外は、互換性のために `SocketException` も実装しています。なので `on SocketException catch` で捕まえているコードは、差し替えると素通りします。3つに共通するのは `ClientException` です。

dioでは、タイムアウトは常に `receiveTimeout`、通信の失敗は `unknown` になり、`connectionTimeout` や `connectionError` は返ってきません。

#### その他

cronet_httpとcupertino_httpが対応しているのは、Android・iOS・macOSだけです。WindowsのWinHTTP対応の要望（[dart-lang/http#1837](https://github.com/dart-lang/http/issues/1837)）には、Dartチームが取り組む可能性は低い、という回答でした。

## おわりに

`package:http`、というより `dart:io` には、あまり語られないものの把握しておくべきクセがあります。proxyや証明書のことを考えると、ネイティブのHTTPクライアントを利用するのが安牌なのではないかなと思っています。
