## はじめに

2026年9月19日、openapi-typescriptがメンテナンスモードに入り、今後は更新しないことが告知されました。

https://github.com/openapi-ts/openapi-typescript/issues/2874

告知によると、セキュリティパッチも含めて更新はなく、利用者には別のプロジェクトへの移行が求められています。最近のOSS開発者への攻撃が増していることも述べられており、大変つらい気持ちです。本当に嫌な状況になりましたね。

---

とはいえ、利用者としては移行先が必要です。openapi-typescriptとopenapi-fetchの「OpenAPIの定義をそのままTypeScriptの型にして、薄い `fetch` のラッパーで呼ぶ」という形が気に入っていたので、同じ方針のツールを自作しました。

作ってみると結構便利なものになりました。特徴は次の4つです。

- 速い: GitHubやStripeの大きな定義でも、型の生成は0.3秒ほど
- 依存が少ない: 依存は `yaml` だけで、クライアントは何もimportしない
- クライアントが便利: openapi-fetchではできなかった、返却値をステータスコードごとに型チェックできる
- OpenAPIの定義に忠実: TypeScriptで表現できる範囲で、スキーマが受け付ける値を型に反映する

https://github.com/koji-1009/kanagata

https://www.npmjs.com/package/kanagata

名前の由来は「金型」です。ピタゴラスイッチのクッキー型の型の歌がイメージです。よろしくお願いします。

## kanagataでできること

できることは2つだけです。

- `kanagata generate`: OpenAPI 3.0 / 3.1 / 3.2（JSONまたはYAML）から、`.d.ts` を1ファイル生成する
- `kanagata/client`: 生成した型で型付けされた、`fetch` の上の関数を1つ提供する

早速動かして行きましょう。適当なプロジェクトを作り、addします。

```sh
pnpm add -D kanagata
pnpm kanagata generate openapi.yaml -o src/api/schema.d.ts
```

たとえば、こんなOpenAPIの定義があるとします。

```yaml:openapi.yaml
openapi: 3.1.0
info:
  title: Example
  version: 1.0.0
paths:
  /users/{id}:
    get:
      operationId: getUser
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: integer
      responses:
        "200":
          description: ok
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/User"
        "404":
          description: not found
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/Problem"
components:
  schemas:
    User:
      type: object
      required: [id, name]
      properties:
        id:
          type: integer
          readOnly: true
        name:
          type: string
        email:
          type: [string, "null"]
    Problem:
      type: object
      required: [message]
      properties:
        message:
          type: string
```

`kanagata generate` すると、次の `.d.ts` が出力されます。

```ts:schema.d.ts
// Generated by kanagata. Do not edit.

export interface paths {
  "/users/{id}": {
    get: operations["getUser"];
  };
}

export interface operations {
  getUser: {
    parameters: {
      path: {
        id: number;
      };
    };
    responses: {
      200: {
        content: {
          "application/json": User;
        };
      };
      404: {
        content: {
          "application/json": Problem;
        };
      };
    };
  };
}

export interface schemas {
  User: User;
  Problem: Problem;
}

export type User = {
  id: number;
  name: string;
  email?: string | null;
};

export type UserInput = {
  name: string;
  email?: string | null;
};

export type Problem = {
  message: string;
};
```

イメージ通りのものが出力されています。やったね。

### クライアント

生成した `paths` を `createClient` に渡します。

```ts
import { createClient } from "kanagata/client";
import type { paths, User } from "./api/schema";

const api = createClient<paths>({ baseUrl: "https://api.example.com" });

const res = await api.get("/users/{id}", { path: { id: 1 } });
if (res.status === 200) {
  const user: User = res.data;
} else {
  res.data.message; // 404のbody
}
```

戻り値は `{ status, ok, data, response }` で、OpenAPIに書かれたステータスコードごとのunionです。`status` で絞り込むと、`data` の型もそのステータスのものになります。

パスやパラメーターを間違えると、型エラーになります。

```ts
await api.get("/users/{id}", { path: { id: "1" } });
// error TS2322: Type 'string' is not assignable to type 'number'.

await api.get("/users/{id}");
// error TS2554: Expected 2 arguments, but got 1.

await api.get("/user/{id}", { path: { id: 1 } });
// error TS2345: Argument of type '"/user/{id}"' is not assignable to parameter of type '"/users/{id}"'.

const res = await api.get("/users/{id}", { path: { id: 1 } });
res.data.name;
// error TS2339: Property 'name' does not exist on type 'User | Problem'.
```

認証やリトライ、ログは、`fetch` を差し替えて実装します。

```ts
const api = createClient<paths>({
  baseUrl: "https://api.example.com",
  fetch: (request) => {
    request.headers.set("authorization", `Bearer ${token}`);
    return fetch(request);
  },
});
```

ミドルウェアの仕組みは、意図的に用意していません。汎用的な仕組みを用意するより、素朴な設計と実装にして、任意の `fetch` を差し込んでもらった方が良いだろうと考えています。

### 返却値をステータスごとに型チェックできる

openapi-fetchと比べて一番便利なのが、ここです。

openapi-fetchの戻り値は `{ data, error, response }` です。`data` は2xxのレスポンスをすべてまとめたunion、`error` はそれ以外のレスポンスをすべてまとめたunionで、`response` はただの `Response` です。そのため、`response.status` で分岐しても、`error` の型は絞り込まれません。

上の定義に、400のレスポンスを足してみます。`ValidationError` は、`errors: string[]` を持つスキーマです。

```yaml
        "400":
          description: invalid
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/ValidationError"
```

openapi-fetchでは、400で分岐しても `error` は `ValidationError | Problem` のままです。

```ts
const client = createClient<paths>({ baseUrl: "https://api.example.com" }); // openapi-fetch
const { error, response } = await client.GET("/users/{id}", {
  params: { path: { id: 1 } },
});
if (error && response.status === 400) {
  error.errors;
  // error TS2339: Property 'errors' does not exist on type ...
  //   Property 'errors' does not exist on type '{ message: string; }'.
}
```

kanagataでは、`status` で分岐すると `data` がそのステータスの型になります。

```ts
const res = await api.get("/users/{id}", { path: { id: 1 } });
if (res.status === 400) {
  res.data.errors; // ValidationError
} else if (res.status === 404) {
  res.data.message; // Problem
} else {
  res.data.name; // User
}
```

200と201で返す内容が違う、400と404でbodyの形が違う、といったAPIでも、型アサーションなしで書けます。`4XX` のような範囲や `default` も型になり、`default` の `ok` は `boolean` なので、`status` か `ok` で絞り込みます。

:::message
openapi-fetch側の確認は、openapi-fetch 0.17.0に、kanagataが生成した型を渡して行いました。openapi-fetchの型定義でも、戻り値の `response` は `Response` で、`error` はエラーのレスポンスをまとめた1つの型です。
:::

### React Queryのhookを書く

openapi-typescriptのリポジトリには、[openapi-react-query](https://www.npmjs.com/package/openapi-react-query) や [swr-openapi](https://www.npmjs.com/package/swr-openapi) もあります。kanagataはhookを生成しませんが、公開している型を使うと、どのパスにも型が付く汎用のhookを数行で書けます。

```ts
import { useQuery } from "@tanstack/react-query";
import {
  type ArgsOf,
  createClient,
  type NotOkResult,
  type OkResult,
  type PathsOf,
  type ResultOf,
} from "kanagata/client";
import type { paths } from "./api/schema";

const api = createClient<paths>({ baseUrl: "https://api.example.com" });

export function useApiQuery<Path extends PathsOf<paths, "get">>(
  path: Path,
  ...args: ArgsOf<paths, "get", Path>
) {
  type R = ResultOf<paths, "get", Path>;
  return useQuery<OkResult<R>["data"], NotOkResult<R>>({
    queryKey: [path, ...args],
    queryFn: async () => {
      const res = await api.get(path, ...args);
      if (!res.ok) throw res;
      return res.data;
    },
  });
}
```

| 型 | 意味 |
| --- | --- |
| `PathsOf<paths, "get">` | GETを持つパスのunion |
| `ArgsOf<paths, "get", Path>` | そのパスを呼ぶときの、パスより後ろの引数 |
| `ResultOf<paths, "get", Path>` | そのパスの戻り値（ステータスごとのunion） |
| `OkResult<R>` / `NotOkResult<R>` | `if (res.ok)` で分かれる、それぞれの側の戻り値 |

2xxを `data` に、それ以外を `error` として投げます。`error` もステータスごとのunionなので、`status` で分岐するとbodyの型が絞り込まれます。

```ts
const { data, error } = useApiQuery("/users/{id}", { path: { id } });
if (error?.status === 400) error.data.errors; // ValidationError
if (error?.status === 404) error.data.message; // Problem
data?.name; // User
```

hookの中にも、呼び出す側にも、型アサーションはありません。パスやパラメーターを間違えれば、`api.get` を直接呼ぶときと同じく型エラーになります。

`Extract<R, { ok: true }>` で書くと、`ok` が `boolean` になる `default` のレスポンスが落ちてしまいますが、`OkResult` / `NotOkResult` は `default` を両側に残します。

## 設計で考えたこと

### 依存を減らす

サプライチェーン攻撃を考えると、依存は少ないほうが良いです。kanagataの依存は、CLIがYAMLを読むための[yaml](https://github.com/eemeli/yaml)だけです。yaml自体も依存を持ちません（ほかのツールとの比較は後述）。

実は、yamlもdropして、YAMLの定義は[yq](https://github.com/mikefarah/yq)などでJSONに変換してもらっても良いかなと思っていました。ただ、流石に不便だなと思って入れています。

クライアント（`src/client.ts`）は何もimportしていません。アプリにバンドルされるのは、この1ファイルだけです。

### クライアントを自分のコードにできる

`kanagata init` を使うと、クライアントのソース（TypeScriptの1ファイル）をプロジェクトにコピーできます。

```sh
kanagata init -o src/api/client.ts
```

コピーしたファイルは、`kanagata/client` の代わりにimportして、自由に書き換えられます。万が一kanagataの更新が止まっても、実行時に動くコードは手元に残ります。好きにいじってもらっても、なんらかの事情がkanagataに生じたので一時的にワークアラウンドしてもらっても良しです。

この仕組みは開発途中のあれこれで追加し、そのままにしています。ライブラリを入れた後、別のものに入れ替えざるを得ないことがあります。そういう時に、結構便利になりそうです。

### スキーマが受け付ける値に型を合わせる

型は、ほかのツールの出力ではなく、スキーマが受け付ける値に合わせています。たとえば次のような扱いです。

- `allOf` や隣にある `type` などはintersectionで組み合わせ、`oneOf` / `anyOf` はunionにする（`A & B & (C | D)`）
- `oneOf` のメンバーのうち、キーを必須にするだけのものは、互いのキーを持たない型にする。「どれか1つだけ」を、TypeScriptで表せる範囲で型にするため
- `discriminator` は読まない。OpenAPI 3.0.4 / 3.1.1で、受け付ける値を変えてはいけないとされているため^["Note that `discriminator` MUST NOT change the validation outcome of the schema."（[OpenAPI 3.0.4](https://spec.openapis.org/oas/v3.0.4.html#discriminator-object)、[OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html#discriminator-object) の Discriminator Object）]
- `not` や `if` / `then` / `else` など、TypeScriptで表せないキーワードは無視して、警告を出す

仕様の文言と実際の使われ方がずれているところは、既定では仕様の文言に従い、使われ方に合わせた読み方はオプションで選べるようにしています。OpenAPI 3.0の `nullable` がその例です（後述）。

テストは、手書きの入力と期待する `.d.ts` の組で書いています。加えて、GitHub・Stripe・Petstoreの定義を固定したコミットで取得し、生成した型を `tsc` で検査しています。

### OpenAPI 3.2

OpenAPI 3.2で追加された `query` メソッド、`additionalOperations`、`in: querystring`、`$self` なども読みます。`additionalOperations` に書かれた `COPY` のようなメソッドは、`api.request` で呼び出します。

```ts
await api.request("COPY", "/files/{name}", { path: { name: "a.png" } });
```

私自身、まだ `query` メソッドを使ったことがないので何ともなのですが、引数の並びを見るに大体こんな感じじゃないかなって気はしています。手書きするのか？ という気はしますが、手書きできる様にしておくのも、また大事なはず。

### AIに書かせ、器は人が決める

kanagataのコードは、AI（Opus 5.5）に書かせています。その代わり、何を正しいとするかは人が決め、リポジトリの [AGENTS.md](https://github.com/koji-1009/kanagata/blob/main/AGENTS.md) にルールとして書いています。主なルールは次のとおりです。

1. テストを先に書く。失敗するspecケースかテストで再現してから、`src/` を触る
2. 期待する出力は手で書く。`expected.d.ts` は1行ずつJSON Schemaの意味と照らし合わせる
3. 型はスキーマが受け付ける値に合わせる。ほかの生成ツールの出力には合わせない
4. カバレッジは100%。どの入力も通らない分岐は、無理にテストせず消す
5. 実際に公開されている定義を対象にする。欠陥と呼ぶ前に、実際の定義でそのパターンを示す
6. READMEと `docs/` が利用者との契約。出力やCLIが変わるなら、同じ変更で更新する
7. 推測しない。壊れたスキーマを救わない。既定は仕様の文言で、慣習はオプションで読む

AIがどれだけコードを書いても、この器から外れたものはテストを通りません。器があるので、型の内部表現もJSONのパーサーも、既存のライブラリや過去との互換に寄りかからず、正面から作れました。次の節で比べる型の正確さは、この作り方から来ていると考えています。

openapi-typescriptの告知には、こんな一節がありました。

> Code generation is an underrated skill. Even in a world where agents are writing code, writing code that writes code is a skill too few engineers hone.

コードを書くコードを、AIに書かせる時代になりました。それでも、何が正しい出力かを決めて、器として残すのは人の仕事なのだと思います。

```js:bench.mjs
// Times TypeScript type generation from OpenAPI documents with each tool.
// usage: node bench.mjs <openapi.json|yaml>... [--runs N]
import { spawnSync } from "node:child_process";
import { mkdirSync, readFileSync, writeFileSync } from "node:fs";
import { basename, dirname, extname, join, resolve } from "node:path";

const args = process.argv.slice(2);
const at = args.indexOf("--runs");
const runs = at === -1 ? 5 : Number(args.splice(at, 2)[1]);
const specs = args.map((s) => resolve(s));
if (specs.length === 0) {
	console.error("usage: node bench.mjs <openapi.json|yaml>... [--runs N]");
	process.exit(2);
}

// Tools are resolved, and run, from the directory this script is in.
const cwd = import.meta.dirname;
const out = join(cwd, ".bench-out");

/** The path of a package's CLI, from its package.json `bin`. */
function bin(pkg, name) {
	const file = join(cwd, "node_modules", pkg, "package.json");
	const { version, bin } = JSON.parse(readFileSync(file, "utf8"));
	const rel = typeof bin === "string" ? bin : bin[name];
	return { version, path: join(dirname(file), rel) };
}

const tools = [
	{
		name: "kanagata",
		pkg: "kanagata",
		args: (cli, spec, dir) => [cli, "generate", spec, "-o", join(dir, "schema.d.ts")],
	},
	{
		name: "openapi-typescript",
		pkg: "openapi-typescript",
		args: (cli, spec, dir) => [cli, spec, "-o", join(dir, "schema.d.ts")],
	},
	{
		name: "@hey-api/openapi-ts",
		pkg: "@hey-api/openapi-ts",
		bin: "openapi-ts",
		args: (cli, spec, dir) => [cli, "-i", spec, "-o", dir, "-p", "@hey-api/typescript", "-s", "--no-log-file"],
	},
	{
		name: "kubb",
		pkg: "kubb",
		args: (cli, spec, dir) => {
			const config = join(dir, "kubb.config.mjs");
			writeFileSync(
				config,
				`import { defineConfig } from "kubb";
import { pluginTs } from "@kubb/plugin-ts";
export default defineConfig({
  input: ${JSON.stringify(spec)},
  output: { path: ${JSON.stringify(join(dir, "gen"))}, clean: true },
  plugins: [pluginTs()],
});
`,
			);
			return [cli, "generate", "--config", config, "-s"];
		},
	},
];

const env = { ...process.env, KUBB_DISABLE_TELEMETRY: "1" };
const results = [];
for (const spec of specs) {
	const name = basename(spec, extname(spec));
	for (const tool of tools) {
		let cli;
		try {
			cli = bin(tool.pkg, tool.bin ?? tool.pkg);
		} catch {
			results.push({ spec: name, tool: tool.name, note: "not installed" });
			continue;
		}
		const dir = join(out, name, tool.name.replace(/[@/]/g, "_"));
		mkdirSync(dir, { recursive: true });
		const argv = tool.args(cli.path, spec, dir);
		const times = [];
		let failed;
		for (let i = 0; i < runs && !failed; i++) {
			const t = performance.now();
			const r = spawnSync(process.execPath, argv, { cwd, env, encoding: "utf8" });
			const ms = performance.now() - t;
			if (r.status !== 0) failed = (r.stderr || r.stdout).trim().split("\n").slice(-3).join(" / ");
			else times.push(ms);
		}
		if (failed) {
			results.push({ spec: name, tool: `${tool.name} ${cli.version}`, note: `failed: ${failed}` });
			continue;
		}
		times.sort((a, b) => a - b);
		const mid = Math.floor(times.length / 2);
		const median = times.length % 2 === 0 ? (times[mid - 1] + times[mid]) / 2 : times[mid];
		results.push({
			spec: name,
			tool: `${tool.name} ${cli.version}`,
			median: (median / 1000).toFixed(2),
			min: (times[0] / 1000).toFixed(2),
		});
	}
}

console.log(`Node ${process.version}, ${runs} runs each, seconds\n`);
console.log("| spec | tool | median | min |");
console.log("| --- | --- | --- | --- |");
for (const r of results)
	console.log(`| ${r.spec} | ${r.tool} | ${r.median ?? r.note} | ${r.min ?? ""} |`);
console.log(`\nOutput: ${out}`);
```

:::

### 依存

それぞれを空のディレクトリに `npm install` したときに入るパッケージの数です。

openapi-typescriptはopenapi-fetchと、Kubbは `@kubb/plugin-ts` と合わせた数です。openapi-typescriptと@hey-api/openapi-tsは、peer dependencyの `typescript` も入るので、それを除いて数えています。

| | パッケージ数 |
| --- | --- |
| kanagata | 2（kanagata、yaml） |
| openapi-typescript + openapi-fetch | 34 |
| @hey-api/openapi-ts | 51 |
| kubb + @kubb/plugin-ts | 88 |

kanagataは `typescript` をpeer dependencyに持ちません。機能を絞ったためではありますが、依存は削れるところまで削れたかなと思います。

### 正確さ

生成された型は、4つとも `strict` かつ `skipLibCheck: false` の `tsc` でエラーなく通りました（Kubbの出力は拡張子なしでimportするので、`moduleResolution: bundler` で検査しました）。そのうえで、`components.schemas` の型を1つずつ、TypeScriptのcheckerで互いに代入できるかを調べました。

| 定義 | openapi-typescriptと一致 | @hey-api/openapi-tsと一致 | Kubbと一致 |
| --- | --- | --- | --- |
| GitHub（1010） | 564（639） | 843（803） | 457（480） |
| Stripe（1538） | 912（1228） | 1171（1123） | 912（1228） |

括弧の外はkanagataの既定、括弧内は `--loose-nullable` を付けた場合です。既定では、後述する `nullable` の読み方の違いも加わります。GitHubのKubbの列は、型の名前の付け方が違って対応を取れなかった28個を除いています。

この数は、kanagataの型と一致した数で、正確さの点数ではありません。一致しない型は、受け付ける値が異なるということです。どちらが定義に忠実かは、個別にスキーマと照らして確かめます。

なお、一致しない型の多くは、参照先の型が違うことによるものです。原因を辿ると、少数のパターンにまとまりました。それぞれ、定義どおりの値を代入して `tsc` で確かめました。詳しく見たい項目を開いてください。

:::details `default` があるプロパティが必須になる（openapi-typescript）

GitHubの `branch-protection.lock_branch.enabled` は、`default: false` を持ちますが、`required` にはありません。

```json
"lock_branch": {
  "type": "object",
  "properties": {
    "enabled": { "default": false, "type": "boolean" }
  }
}
```

JSON Schemaの [`default`](https://json-schema.org/draft/2020-12/json-schema-validation#name-default) は注釈で、受け付ける値を変えません。しかし、openapi-typescriptは `default` があるプロパティを必須にします（[`--default-non-nullable`](https://openapi-ts.dev/cli) が既定で有効）。

```ts
const lock: NonNullable<components["schemas"]["branch-protection"]["lock_branch"]> = {};
// error TS2741: Property 'enabled' is missing in type '{}' but required in type '{ enabled: boolean; }'.
```

GitHubの定義では、`repository.is_template` などの多くのプロパティがこれで必須になり、`repository` を参照する型すべてに広がります。

:::

:::details プロパティのないobjectに、何も入れられない（openapi-typescript）

GitHubの `authentication-token.permissions` は、`type: object` だけのスキーマです。定義の `example` には、`{ "issues": "read", "deployments": "write" }` が書かれています。

openapi-typescriptは、これを `Record<string, never>` にします。定義に書かれた例そのものが代入できません。

```ts
const permissions: components["schemas"]["authentication-token"]["permissions"] = {
  issues: "read",
  deployments: "write",
};
// error TS2322: Type 'string' is not assignable to type 'never'.
```

Stripeでは、`components.schemas` のうち104個がプロパティのないobjectで、openapi-typescriptの出力（paths込み）には `Record<string, never>` が776か所あります。kanagataと@hey-api/openapi-tsは、どちらも任意のobjectを受け付けます（kanagataは `Record<string, unknown>`）。Kubbは `object` にするので、`type: object` が受け付けない配列も代入できてしまいます。

:::

:::details `discriminator` が参照先の型を変える（openapi-typescript）

GitHubの定義には、`user_view_type` で `public-user` と `private-user` を分ける `discriminator` があります。`public-user.user_view_type` 自体は、必須でない `type: string` です。

openapi-typescriptは、`discriminator` の `mapping` の値を参照先に書き込みます。そのため、`public-user` を使うすべての場所で、`user_view_type` が必須の `"public"` になります。

```ts
const viewType: components["schemas"]["public-user"]["user_view_type"] = undefined;
// error TS2322: Type 'undefined' is not assignable to type '"public"'.
```

OpenAPI 3.0.4 / 3.1.1では、`discriminator` は受け付ける値を変えてはいけないとされています^["Note that `discriminator` MUST NOT change the validation outcome of the schema."（[OpenAPI 3.0.4](https://spec.openapis.org/oas/v3.0.4.html#discriminator-object)、[OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html#discriminator-object) の Discriminator Object）]。前述のとおり、kanagataは `discriminator` を読まないので、`user_view_type` は必須でない `string` のままです。

:::

:::details 「どれか1つは必須」が消える（openapi-typescript、@hey-api/openapi-ts）

GitHubの `secret-scanning-custom-pattern-to-update` は、`anyOf` と `required` で「`pattern` などのどれか1つは必須」を表しています。

```json
"required": ["custom_pattern_version"],
"anyOf": [
  { "required": ["pattern"] },
  { "required": ["start_delimiter"] },
  { "required": ["end_delimiter"] },
  { "required": ["must_match"] },
  { "required": ["must_not_match"] }
]
```

openapi-typescriptはこれを `{ ... } | unknown | unknown | ...` にするので、型全体が `unknown` になり、`42` でも代入できます。@hey-api/openapi-tsは `unknown & { ... }` にするので、どれか1つは必須という条件が消えます。kanagataとKubbはこの条件を型で表すので、更新するフィールドがないリクエストは型エラーになります。

```ts
const update: schemas["secret-scanning-custom-pattern-to-update"] = {
  custom_pattern_version: "v1",
};
// error TS2322: Type '{ custom_pattern_version: string; }' is not assignable to type 'SecretScanningCustomPatternToUpdate'.
```

:::

:::details 「どれか1つだけ」が守られない（openapi-typescript、@hey-api/openapi-ts、Kubb）

GitHubのCodeQLの `code-scanning/create-variant-analysis` のリクエストbodyは、`oneOf` で「`repositories`、`repository_lists`、`repository_owners` のどれか1つだけ」を表しています。説明にも "Precisely one property from `repositories`, `repository_lists` and `repository_owners` is required." と書かれています。

```json
"oneOf": [
  { "required": ["repositories"] },
  { "required": ["repository_lists"] },
  { "required": ["repository_owners"] }
]
```

`oneOf` は、ちょうど1つのメンバーに合う値だけを受け付けます。そのため、2つ指定したリクエストも、1つも指定しないリクエストも、定義では受け付けません。

| ツール | 2つ指定 | 1つも指定しない |
| --- | --- | --- |
| kanagata | 型エラー | 型エラー |
| openapi-typescript | 通る | 通る |
| @hey-api/openapi-ts | 通る | 通る |
| Kubb | 通る | 型エラー |

kanagataは、キーを必須にするだけのメンバー同士では、それぞれがほかのメンバーのキーを持たない型にしています。

```ts
type RequestBody =
  operations["code-scanning/create-variant-analysis"]["requestBody"]["content"]["application/json"];

const body: RequestBody = {
  language: "javascript",
  query_pack: "...",
  repositories: ["octocat/hello-world"],
  repository_owners: ["octocat"],
};
// error TS2322: ... Types of property 'repository_owners' are incompatible.
//   Type 'string[]' is not assignable to type 'undefined'.
```

ほかの制約を持つメンバーが混ざる `oneOf` では、TypeScriptで「ほかのメンバーに合わない」を表せないので、これまでどおりunionにしています（[docs/types.md](https://github.com/koji-1009/kanagata/blob/main/docs/types.md#oneof)）。

:::

:::details `int64` が `bigint` になる（Kubb）

GitHubの `simple-user.id` は、`type: integer` に `format: int64` が付いています。GitHubの定義には、`format: int64` が344か所あります。

```json
"id": { "type": "integer", "format": "int64", "example": 1 }
```

Kubbは、これを `bigint` にします。しかし、`JSON.parse` は数値を `number` で返すので、レスポンスの値は `bigint` になりません。

```ts
const id: SimpleUser["id"] = 1;
// error TS2322: Type 'number' is not assignable to type 'bigint'.
```

GitHubでKubbと一致しない型の多くは、ユーザーやリポジトリの `id` がこれで `bigint` になり、参照する型に広がったものです。kanagataは、`format` に関わらず `integer` を `number` にします。

なお、`number` では、安全な整数の範囲（`Number.MAX_SAFE_INTEGER`）を超える値の精度は保証できません。`bigint` で正確に扱うには、JSONをパースする時点で対応が必要です。ただ、Kubbのクライアント（`@kubb/plugin-client` 6.0.1）もレスポンスを `JSON.parse` で読むので、型が `bigint` でも値は `number` になります。

:::

#### `nullable` をどう読むか（OpenAPI 3.0）

OpenAPI 3.0の `nullable: true` は、仕様の文言（3.0.3）では、同じスキーマの `type` に `null` を足すだけです^["A `true` value adds `"null"` to the allowed type specified by the `type` keyword, only if `type` is explicitly defined within the same Schema Object."（[OpenAPI 3.0.3 の Schema Object](https://spec.openapis.org/oas/v3.0.3.html#schemaNullable)）]。

- `type` がなければ効かない（`anyOf` や `allOf` だけのスキーマ）
- `$ref` の隣では、ほかのキーワードと同じく無視される
- `enum` に `null` がなければ、`null` は受け付けない

一方で、定義を書く側は、これらの形で「この値かnull」を表していることが多いようです。GitHubの定義は3.0.3、Stripeは3.0.0で、仕様の文言では効かない `nullable: true` がたくさんあります。

| 定義 | `nullable: true` | うち `type` なし | うち `null` のない `enum` |
| --- | --- | --- | --- |
| GitHub | 4025 | 148 | 74 |
| Stripe | 2795 | 633 | 261 |

たとえば、Stripeの `invoice.default_payment_method` は `anyOf: [string, payment_method]` に `nullable: true` が付いていて、`type` がありません。GitHubの `dependabot-alert.dismissed_reason` は、`null` のない `enum` です。

```json
"dismissed_reason": {
  "type": "string",
  "nullable": true,
  "enum": ["fix_started", "inaccurate", "no_bandwidth", "not_used", "tolerable_risk"]
}
```

GitHubの定義に載っているDependabotアラートのレスポンス例では、`dismissed_reason` は `null` です。

型を生成するツールの多くは、「この値かnull」と読んで `null` を足します。`null` のない `enum` について、同じ定義で6つのツールを試した結果です。

| ツール | `null` のない `nullable` な `enum` |
| --- | --- |
| kanagata 0.3.1 | `null` を含めない（`--loose-nullable` で含める） |
| openapi-typescript 7.13.0 | `null` を含める |
| Kubb 5.19.0（`@kubb/plugin-ts` 5.5.1） | `null` を含める |
| [orval](https://orval.dev/) 8.47.0 | `null` を含める |
| [swagger-typescript-api](https://github.com/acacode/swagger-typescript-api) 13.14.0 | `null` を含める |
| @hey-api/openapi-ts 0.99.0 | `null` を含めない |

`type` のない `nullable: true` には、openapi-typescriptも@hey-api/openapi-tsもKubbも `null` を足します。

kanagataは0.3.0で、既定を仕様の文言どおりにしました。慣習どおりの読み方は、`--loose-nullable` で選べます。既定は仕様に従い、定義の書き方に合わせたいときはオプションで選ぶ、という形が一番健全だと考えました。

```sh
kanagata generate openapi.json -o schema.d.ts --loose-nullable
```

| | 既定 | `--loose-nullable` |
| --- | --- | --- |
| Stripe `invoice.default_payment_method` | `string \| PaymentMethod` | `string \| PaymentMethod \| null` |
| GitHub `dependabot-alert.dismissed_reason` | `"fix_started" \| … \| "tolerable_risk"` | `"fix_started" \| … \| "tolerable_risk" \| null` |

StripeやGitHubのように「この値かnull」の意味で書かれた定義には、`--loose-nullable` を付けます（例ごとの出力は [docs/types.md](https://github.com/koji-1009/kanagata/blob/main/docs/types.md#nullable-30) にあります）。ライブラリAPIでは、`generate(src, source, { looseNullable: true })` で指定します。

---

まとめると、ほかのツールの型が定義からずれていたところを、kanagataは定義どおりにしています。

定義より厳しい型（`default` で必須、空のobject、`discriminator`）は広げ、定義より緩い型（「どれか1つは必須」や「どれか1つだけ」の欠落、配列も入る `object`）は狭め、実行時の値と合わない型（`bigint`）は `number` にしています。`nullable` も既定では仕様どおりに読み、慣習どおりの読み方は `--loose-nullable` で選べます。

## openapi-fetchからの移行

ほぼ自分用に。もしも移行を試したい方がいたら、お手元のエージェントに読ませてみてください。

---

openapi-fetchと書き方が近いので、移行は機械的にできます。

| | openapi-fetch | kanagata |
| --- | --- | --- |
| 型の生成 | `npx openapi-typescript schema.yaml -o schema.d.ts` | `npx kanagata generate schema.yaml -o schema.d.ts` |
| import | `import createClient from "openapi-fetch"` | `import { createClient } from "kanagata/client"` |
| メソッド | `client.GET(...)` | `api.get(...)` |
| パラメーター | `{ params: { path, query } }` | `{ path, query }` |
| 戻り値 | `{ data, error, response }` | `{ status, ok, data, response }`（ステータスごとのunion） |

戻り値の形が違うので、`if (error)` で分けているところは、`res.ok` や `res.status` で分けるように書き換えます。

OpenAPI 3.0の定義では、`nullable` の読み方の違いで、`null` の付き方がopenapi-typescriptと変わることがあります。openapi-typescriptと同じように「この値かnull」と読ませたい場合は、`--loose-nullable` を付けて生成します。

ミドルウェアの代わりは `fetch` の差し替えで、レスポンスの検証は `onData` で行います。zodの差し込みなんかもできます。
