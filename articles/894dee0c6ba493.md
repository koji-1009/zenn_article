## はじめに

https://x.com/D_R_1009/status/2101493862682542299

FlutterのWidgetを、任意のタイミングでPNGとして取り出すCLIを作りました。

https://pub.dev/packages/shutter

## 見た目の変更は、見た目でしか確認できない

Flutterを採用しているプロジェクトでは、多くのケースで、PR(やMR)のテンプレートに**スクリーンショットの添付欄**があるのではないでしょうか。筆者は結構ズボラなので、めんどくさいな〜と思いつつiPhone simulatorを立ち上げ、command+Sでスクショをぽちぽち撮っています。

ただ、スクショの力は侮れません。コードを書いている時には完璧だと思っていたものが、実際に画像を比べてみると、全然ダメなことが結構あります。Flutterでは任意のプラットフォームで確認すれば大体大丈夫ですが、このステップの重要性は変わりません。

また、AIエージェントにコードを書かせてみるようになっても、このフローは変わりません。AIが作ったコードを「え〜、これで直ってるの〜？」と言いながら実機確認するのが常です。MCPなどでスクリーンショットを撮るまで自走できるようになってきましたが、ビルドが挟まるとそこそこ時間がかかります。

---

人間が書いていても、AIが書いていても、**見た目**の確認はネックです。ここを改善できれば、人間はAIにコードを書かせてPRを作るところまでお任せできるようになります。PRを作らなくとも、サッとCLIで「差分の画像出して」と依頼できるだけで、開発は楽チンになるはずです。

さてFlutter v3.47から [Widget Previewer](https://docs.flutter.dev/tools/widget-previewer) が安定版になりました。`@Preview` を付けた関数を `flutter widget-preview start` で一覧表示するツールです。筆者もあんまり使いこなせていないのですが、VS Codeのサイドバーからもチェックでき、便利そうな気配を感じています。

ただ、あくまでも、これは**開発者が開発中のコードをサッと確認する**仕組みです。というのも、現在のWidget Previewerには画像出力の機能がありません。結果、せっかくWidget単体の画像があっても、それをOSのスクリーンショット機能などを経由して画像化するしかありません。

`shutter` は、この出口を作るツールです。`@Preview` をPNGとして書き出します。プレビューを書いていないWidgetも、コマンドラインに式を渡せば撮れます（後述）。

| before | after | `diff --images` |
| --- | --- | --- |
| ![変更前のNotificationTile](/images/894dee0c6ba493/notification_tile_before.png) | ![変更後のNotificationTile](/images/894dee0c6ba493/notification_tile_after.png) | ![差分ピクセルを赤で示した画像](/images/894dee0c6ba493/notification_tile_diff.png) |

通知タイルのレイアウトを変え、本文を「…」で切らずに折り返すようにしたときの3枚です。以降の使い方では、ボタンのプレビューを例にします。

## 使い方

### インストール

```bash
dart install shutter
```

対象プロジェクトの条件は、Flutter 3.47以上と、`dev_dependencies` の `flutter_test` だけです。プロジェクト側に `shutter` への依存は増えません。環境の確認は `shutter doctor` で行います。

### `@Preview` を"撮影"する

`shutter shot` は、`lib/` 配下の `@Preview` 関数を持つファイルを受け取ります。既存のプレビューがあるなら、そのまま被写体になります。

プレビューのないWidgetには、小さなプレビューファイルを書きます。置き場所は `shutter` の規約で、アプリなら `lib/preview/`、パッケージなら `lib/src/preview/` です。

```dart:lib/preview/button_preview.dart
import 'package:flutter/material.dart';
import 'package:flutter/widget_previews.dart';

import '../ui/button.dart';
import '../ui/login_form.dart';

// Only the height is fixed: the button keeps its own width, so padding
// changes show up. A fixed width would stretch the button to that width.

@Preview(name: 'PrimaryButton / short', size: Size.fromHeight(56))
Widget buttonShort() => const PrimaryButton(label: 'OK');

@Preview(name: 'PrimaryButton / long', size: Size.fromHeight(56))
Widget buttonLong() => const PrimaryButton(label: 'Continue to checkout');

@Preview(name: 'PrimaryButton / Japanese', size: Size.fromHeight(56))
Widget buttonJapanese() => const PrimaryButton(label: '長いラベルのボタン 🎉');

@Preview(name: 'LoginForm', size: Size(390, 844))
Widget loginForm() => const LoginForm();
```

被写体のWidget自身にアノテーションは要りません。プレビューファイルがimportして返すだけです。

`size` の指定には意味があります。上のボタンは高さだけを固定しているため、自分の幅のまま描画されます。paddingを変えれば幅が変わり、それが画像に出ます。幅も固定すると、ボタンはその幅まで引き伸ばされてしまいます。最後の `LoginForm` のように画面を撮るときは、両方を固定します。

### 撮影した画像を比べる

編集の前に一度撮影しておきます。1回の `shot` の結果を `shutter` ではrunと呼び、これが比較のもとになります。

```console
summary: {error: 0, ok: 4}

  - id: "559f2ab0c803d820.0"
    status: ok
    name: "PrimaryButton / short"

    png: /path/to/example/.dart_tool/shutter/runs/20260920T105416Z/559f2ab0c803d820.0.png

```

`PrimaryButton` のpaddingを `horizontal: 24` から `horizontal: 40` に変え、もう一度撮ります。そして2つのrunを比べます。

```console

    status: changed
    name: "PrimaryButton / short"

    size: [98.69, 56]
    before_size: [66.69, 56]
    diff_ratio: 0.4337
    before: /path/to/example/.dart_tool/shutter/runs/20260920T105416Z/559f2ab0c803d820.0.png
    after: /path/to/example/.dart_tool/shutter/runs/20260920T105441Z/559f2ab0c803d820.0.png
    diff: /path/to/example/.dart_tool/shutter/diffs/20260920T105442Z/559f2ab0c803d820.0.png

```

ボタンの3つのプレビューが `changed` になり、幅が66.69から98.69へ広がったことが数字で出ます。一方、4つ目の `LoginForm` は `unchanged` でした。この画面も `PrimaryButton` を使っていますが、`CrossAxisAlignment.stretch` で横幅いっぱいに引き伸ばしているため、横のpaddingを変えても描画は変わりません。コードを追うだけだと「使っているのだから変わるはず」と判断してしまうところです。

`--images` を付けると、差分ピクセルを赤で塗った画像も書き出されます。画像やrunのパスは絶対パスで出力されるので、そのまま画像ビューアやPRに渡せます。

---

実機のスクリーンショットと異なるのは、揃えるべき条件がそもそも無い点です。

スクロールしないと見えないWidgetの場合、実機では前後のスクロール量を一致させないと比較になりません。`shutter` はWidgetを単体でも撮れるので、スクロールして画面に出す手順が要りません。サイズも `@Preview` の `size` で決まるため、端末差も入りません。意図して作ったものではなかったのですが、便利に感じています。

### `@Preview` を使わずに"撮影"する

「このWidget、ここで使ったらどう見えるんだろう」を確認したいだけなら、コマンドラインに式を直接渡せます。人間からするとちょっと厳しい操作ですが、AIからすると簡単な気がするので追加してみました。^[ありがとうOpus 5。]

```bash
shutter shot --widget 'PrimaryButton(label: "OK")' \
  --import lib/ui/button.dart --size 200x56
```

`--import` には、その式が必要とする `lib/` 配下のファイルか、`package:` URIを並べます。`--size` を省くと、Widgetは自分のサイズのまま撮られます。内部では、渡された式をその式自身の名前を持つ `Preview` として撮るテストを生成しています。

### 操作して"撮影"する

プレビューが示すのは、コンストラクタで作れる状態だけです。押している最中のボタン、入力済みのフォーム、開いたメニューといった操作の結果の状態は、v0.2.0から、撮影の前に操作を加えて撮れるようになりました。

```bash
shutter shot --widget 'PrimaryButton(label: "Save")' --import lib/ui/button.dart \
  --press text:Save --settle 700
```

| 操作なし | `--press text:Save` |
| --- | --- |
| ![Saveボタン](/images/894dee0c6ba493/save_button.png) | ![押下中のSaveボタン](/images/894dee0c6ba493/save_button_pressed.png) |

操作は、`--tap` と `--enter <対象>=<テキスト>`（どちらも繰り返し可、指定した順に実行）のあとに、`--press`・`--hover`・`--focus` のいずれか1つを置けます。対象は `key:`、`text:`、`label:`、`type:` のいずれかで指定します。`label:` はセマンティクスラベルで、テキストフィールドのラベルやヒント、ボタンの文字列が該当します。対象が見つからない、複数ある、指が届かないといった場合は、そのshotは `error` になります。

```bash
shutter shot --widget 'LoginForm()' --import lib/ui/login_form.dart --size 390x480 \
  --enter 'label:Email=example@example.com' --focus label:Password
```

![Emailに入力し、Passwordにフォーカスしたログインフォーム](/images/894dee0c6ba493/login_form_entered.png)

メニューやダイアログ、ボトムシート、ツールチップは、プレビューの上のオーバーレイに描かれるため、通常の撮影範囲には入りません。`--capture screen` を付けるとビューポート全体を撮るので、これらも写ります。`--viewport` を指定すれば、小さなプレビューにもメニューが開くだけの広さを与えられます。

```bash
shutter shot --widget 'DropdownButton<String>(value: "Newest", items: const [
    DropdownMenuItem(value: "Newest", child: Text("Newest")),
    DropdownMenuItem(value: "Oldest", child: Text("Oldest")),
    DropdownMenuItem(value: "Popular", child: Text("Popular")),
  ], onChanged: (_) {})' \
  --import package:flutter/material.dart \
  --tap 'type:DropdownButton<String>' --capture screen --viewport 240x240 --settle 700
```

![開いたドロップダウンメニュー](/images/894dee0c6ba493/dropdown_opened.png)

`--settle` は、最後の操作から撮影までの時間です（ミリ秒、デフォルトは300）。時計はシミュレートされているので、同じ `--settle` なら同じ画像になります。タップしたボタンのインクは300msの時点ではまだ残っているので、消えた後の状態を撮るなら `--settle 700` が目安です。アニメーションの途中を撮りたいときは、`--settle` を変えて撮り直します。

加えた操作は `shot` の出力に `actions` として記録され、`diff` は2つのrunの操作が異なるときに両方を表示します。操作はshot idに含まれないので、操作なしのrunと操作ありのrunでも、shotどうしが対応づけられます。

## golden testとの違い

Flutterで画像を扱うテストといえば `matchesGoldenFile` です。関係を整理しておきます。

|  | golden test | shutter |
| --- | --- | --- |
| 目的 | 変わっていないことを守る | どう変わったかを見せる |
| 基準画像 | リポジトリにコミットする | 持たない |
| 比較対象 | 基準画像と現在の描画 | 自分で撮った2つのrun |
| 更新 | `--update-goldens` で撮り直す | 概念として存在しない |
| 環境差分 | CIとローカルの差を管理する | 同一マシンの2つのrunを比べるので出ない |
| 書くもの | テストコード | `@Preview` 関数 |
| 終了コード1の意味 | テストが落ちた | 差分があった |

一番の違いは、**基準画像を持たないこと**です。`shutter` の比較は常に「自分が撮った2つのrun」の間で閉じています。CIに置いた基準画像との環境差分に悩む必要がなく、更新の儀式もありません。その代わり、リグレッションを自動で検出する機能もありません。

これは役割の違いです。golden testは変更を止めるための仕組みで、`shutter` は変更を進めるための道具です。開発中の反復では `shutter` で見た目を確認し、仕様が固まった箇所をgolden testで守る、という併用が自然だと考えています。

AIエージェントに任せる観点でも、基準画像を持たない設計には意味があります。golden testをAIに扱わせると、差分が出たときに「基準画像を更新しておきました」で済ませてしまうことがあります。`shutter` には更新できる基準がないので、この誤魔化しの経路がありません。代わりに差分画像が残るため、判断の材料は人間の側に返ってきます。

## AIエージェント

`shutter` はAIエージェントが使うことを前提に設計しています。

### バイナリに同梱したマニュアル

`shutter agent` を実行すると、手順書が出力されます。被写体を決めて、編集前に撮り、編集してからまた撮り、`diff` を読むという流れです。`shutter manual` は概念のリファレンスです。

ドキュメントをバイナリに同梱しているのは、インストールされたバージョンと手順書をずらさないためです。そしてもう1つ、AIが使い方を知らないとゴネる状態を避けるためでもあります。AIからすると `shutter` は未知のパッケージなので、まず間違いなく「私は使い方を知りません」と右往左往します。これをガードするための仕組みです。

パッケージには [agent skill](https://dart.dev/tools/pub/package-skills) の `shutter-visual-check` も同梱しています。「見た目に影響する変更をしたら `shutter` を使う」とAIに伝え、詳細は `shutter agent` を見るように指示する内容です。

```bash
dart run skills@ add koji-1009/shutter
```

### 出力と終了コード

`shot` と `diff` の出力は、`# shutter ai-report v1` で始まるYAMLです。画像やrunのパスは絶対パスなので、そのまま次のコマンドに渡せます。

終了コードは用途別に分けています。

| コマンド | 0 | 1 | 2 |
| --- | --- | --- | --- |
| `shot` | すべて成功 | — | エラーのあるshotがある |
| `diff` | 差分なし | 差分あり | — |
| `doctor` | 問題なし | 失敗した確認項目がある | — |

この区別があるので、AIエージェントは「差分があったから画像を確認する」という分岐を素直に書けるはずです。

### PRに画像を添付

生成された画像は `.dart_tool/shutter/` 以下のファイルです。どこに貼るかは利用者の判断に委ねていますが、GitHubなら `gh` で直接添付できます。

```bash
gh pr comment <number> --attach '<png>#<alt text>'
```

筆者が欲しかったのは、この「PRに画像が付く」状態です。レビュー側の確認コストが変わると考えています。もちろんコードも読むべきですが、その前に、AIが正しく実装できたかどうかを画像で確かめられます。かつ、PRに残るので、後ほど「このPRでは何をしたんだっけな…」と検索するコストも下がるはずです。

### CLIがやらないこと

`shutter` は判断をしません。被写体の選択、変更の良し悪し、投稿先はすべて利用者の決定です。画像を出して、違うピクセルを示すところまでを担当します。

これは [dartrics](https://zenn.dev/koji_1009/articles/f4dd2cb293856b) を作ったときと同じ方針です。CLIを賢くする方向には進まず、判断はAIエージェントに委ねます。^[CLIをいくら賢くしようとしても、筆者の賢さが上限になっちゃいますしね。]

## 制約について

現在の実装は `flutter test` の上でレンダリングしています。ここから来る制約があります。

- 撮影は1プレビューにつき1回。タップや入力、押下・ホバー・フォーカスは撮影前に加えられるが、スクロールとドラッグは撮れない。アニメーションは `--settle` を変えたrunを重ねて撮る
- オンスクリーンキーボードは描かれない。`--enter` の文字はフィールドに入るが、`--capture screen` でもキーボードは写らない
- HTTPが遮断されるため、`NetworkImage` は失敗する
- テストエンジンにはシステムフォントのフォールバックがない。`shutter` はホストのCJKフォントと絵文字フォントを補うが、独自に `fontFamilyFallback` を設定したスタイルには届かない
- フォントはホストのものを使うため、比較する2つのrunは同じマシンで撮る必要がある

エラーは撮影を止めません。オーバーフローやbuild中の例外は `error` のshotとして記録され、原因となる `lib/` の行が `at` に入ります。フレームが描かれていればPNGも残るので、オーバーフローの縞模様がそのまま証拠になります。

## Flutter SDKに関する諸問題

`shutter` を作る過程で、Flutter SDK側に感じたことを書いておきます。

現在のv1は、Widget Previewerが画像を出せないという前提のもとで、`flutter test` を経由して描画しています。これは回避策の積み重ねであって、理想的な設計ではありません。Fontの問題、`flutter/material.dart` が `material_ui/material_ui.dart` に移行する問題など、複数の問題を踏み抜いています。その他、Widget Previewerが `lib/` 配下しか見ない制約なんかの影響も受けています。

これらの問題の大半は `flutter widget-preview` が `ui.Image` を出力してくれれば解決するはずです。`shutter` の内部はエンジン層を差し替えられるよう切ってあるので、SDK側の改善が入れば、runやdiffの設計を変えずに置き換えられます。^[ニーズが確認されれば、改善されるんじゃないかなと思ってます。]

世の中がAIによる実装をサポートする方向に向かっているので、知見を積み上げていけば、良い方向に進む気がしています。Widget Previewerは面白い仕組みなので、気になった方は、ぜひ触ってみてください。

`shutter` は、Flutterの開発ループで人間の手に残りがちだった「見た目の確認」を、画像という形で機械に渡す試みです。人間が手で叩いても便利ですし、AIエージェントに渡しても同じように動きます。見た目に関わる変更をAIに任せている方は、ぜひ試してみてください。

agent skillの使い勝手やPRへの貼り付けについては、筆者もまだ手応えを掴みきれていません。使ってみての感想やご要望があれば、ぜひお寄せください。お待ちしています！
